# Map visual research: more engaging within a small rendering budget

Date: 4 November 2026. Status: research and proposed direction; no product implementation.

## Recommendation

Make the map a **spatial musical score**: quiet geography, crisp route colours, and small visual responses to actual notes. Design serves the product. The signature is seeing where the music happens. Spend the visual budget on that relationship.

Start with theme-aware geography, interactive route focus and fewer competing effects. These can make existing movement more legible without increasing continuous work.

This supplements [the October plan](README.md). Current source inspection supersedes its claim that playheads update through React state: they now use imperative updates. This research also proposes substantially lower trail/effect budgets than that plan. Neither document establishes measured performance gains.

## Evidence and limits

- **Observed in current source:** Leaflet routes over a MapLibre/OpenFreeMap basemap; hardcoded dark map; shared ticker; roughly 30fps imperative playheads; Canvas trails; note ripples; animated automation dashes; route legend and dim inactive routes. References below.
- **Observed in historical screenshots:** reviewed the October [desktop playback](evidence/desktop-playing.png) and [phone](evidence/phone.png) captures. Dense street detail competes with route strokes; the narrow patterned legend makes identity harder to read. These captures are historical, not a fresh UI audit.
- **Observed externally:** opened Mobbin's public navigation collection and three individual screen pages in a browser. Screens are small public previews. App links/full browsing ask for registration; no account was created. Still images establish composition, not animation quality or implementation performance.
- **Inferred:** stronger route/background separation and persistent route focus will make the relationship between lane, place and sound easier to understand. This is a design hypothesis, not user-study evidence.
- **Assumed:** keep the current map stack, Night Timetable tokens and mock-only playback. No new continuous animation system, map engine or data feed.
- No local app was available on ports 3000/3002. No fresh playback, audio or runtime benchmark was performed. Current implementation findings are code-level observations, not visual sign-off.

## Priorities

The cost labels describe expected rendering work, not benchmark results or engineering estimates.

| Priority | Improvement | Visual/interaction specification | Expected runtime cost |
| --- | --- | --- | --- |
| 1 | Quieter basemap in both themes | Remove POIs/minor-road labels; soften local roads; retain river, district names and major axes. Use a true light style. Preserve attribution. | No added animation loop. Style loading still has cost; fewer features are not automatically a measured speedup. |
| 1 | Persistent route focus | Click a lane badge to emphasize that route and show route name, musical role and selected station details. Clear focus returns the mix view. Focus never changes solo, enable or volume. | Event-driven style changes; negligible idle animation work. |
| 1 | Cleaner route hierarchy | Start with a 3px active stroke, selected route 4px with a neutral casing where contrast needs it. Unfocused active routes remain visible; off routes remain explicitly identifiable. Remove broad permanent colour underlays. | Static styling; reducing overdraw may help, subject to profiling. |
| 1 | Progressive stop detail | Show selected-route stops at useful zoom; suppress nonessential stops when zoomed out. On phone show selected/current stop only initially. Prototype zoom 13 as the detail threshold, then tune per city. | Can reduce existing marker and paint work. |
| 2 | Note feedback with restraint | Reuse existing note ripples. One 220ms ring per admitted attack, expanding from 6px to 14px and fading out. Coalesce same-stop attacks; drop excess visuals. No pulse on rests/skipped notes. | Small bounded event cost; no work when there are no admitted effects. |
| 2 | Make movement trustworthy | Cache stop-to-shape mapping so heads follow the displayed polyline instead of cutting stop-to-stop corners. Preserve musical distance/time and fallback for ambiguous geometry. | Preprocessing/cache complexity; avoid repeated geometry searches in the frame loop. |
| 2 | Calm the camera and controls | Preserve user framing during lane edits. Fit mix / Fit route are explicit actions. Remove decorative legend grids; use flat route rows. | Mostly event-driven; avoids repeated automatic refits. |
| Later | Optional expanded listening view | Reuse the same map and renderer in a larger area. Keep transport and a clear exit. | Larger canvas/pixel count can cost more; measure before shipping. |

Do not add 3D buildings, camera orbit, audio-wide bass flashes, waveform overlays, bloom/blur, heatmaps or a larger particle field. The map already has its core animated vocabulary.

## Motion specification

Keep the signature motion tied to musical events. Continuous 1.2-second breathing pulses are currently independent of notes: remove them before adding another effect.

| Moment | Default proposal | Reduced motion |
| --- | --- | --- |
| Route focus | Apply route styles immediately; detail card enters with opacity + 4px translate over 160ms, exits in 100ms | Immediate style/card update |
| Note attack | Existing ring, 220ms maximum; bounded pool | Static selected-stop indication, coalesced to at most 2 changes/second |
| Playhead | Retain existing ~30fps ceiling; no increase | No travelling head/trail; discrete selected-stop updates |
| Fit route/mix | User-requested, at most 250ms; never automatic during playback edits | Instant fit |
| Automation | Prefer a static dashed path by default; retain value/target semantics | Static dashed path |
| Stopped/hidden | No continuous visual effects or stale-event replay | Same |

For small HTML overlays animate only `transform` and `opacity`. Those properties often avoid layout and paint, but this does **not** make Canvas redraws or SVG stroke animations free. Do not overwrite Leaflet's positioning transform: animate an inner child. Use `will-change` only where profiling justifies it. [web.dev animation guidance](https://web.dev/articles/animations-guide)

Observe the OS motion preference for both CSS and imperative drawing; a media-query rule alone cannot stop JavaScript playhead updates. [MDN reduced-motion reference](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)

## Proposed performance envelope

These are conservative starting caps to validate, not claims of safe performance on every device.

- Retain the existing shared ticker and ~30fps dynamic-map ceiling. No per-frame React state or extra rAF loop.
- Keep current trail sampling at most 10 points/head on desktop and 5 on phone. If needed, reduce before adding effects; do not adopt the October plan's 64/32 samples.
- Begin with at most **8 simultaneous attack rings desktop / 4 phone**, one per route+stop. New events replace old visuals at capacity; sound is never dropped or delayed.
- Test an incremental dynamic-overlay CPU target of **p95 ≤2ms per map update** on an agreed desktop and **≤4ms** on the agreed phone. Include style/layout/paint/compositing and GPU pressure in traces; the JS timer alone is incomplete.
- Pause dynamic subscriptions, pending attacks and CSS loops when the map or document is hidden. Cull offscreen dynamic effects; keep geographic caches stable across frames.
- Prefer one shared Canvas for dense dynamic effects. CSS on a few HTML elements can be cheap; hundreds of separately promoted markers can consume memory. Keep existing static-layer memoization and mobile Canvas route path.
- A low-detail fallback removes ripples, then trails, then travelling heads, while keeping readable static routes and focus. If automatic adaptation is added, use rolling windows and hysteresis, not cumulative session p95. User-facing preference can simply say “Reduce motion.”

Validate in stages:

1. Baseline a production build with a saved song and fixed viewport/camera, then compare each visual stage separately. Include Berlin and NYC, 6 and 24 mapped lanes, stopped/playback and pan/zoom. Use the existing `scripts/perf_bench.mjs` as a starting point, not proof of audio quality.
2. Record hardware/browser, frame p95, long frames, blocking time, memory and audio dropout/late-note metrics for matched runs of at least 60 seconds after warmup. Rate metrics are unavailable in the first 20 seconds. Repeat baseline and candidate to expose noise.
3. Inspect browser traces for paint and GPU cost. Reject any repeatable audio-stability regression. Listen to actual output; metrics/build success cannot establish perceived sound or synchronization.
4. Test dark/light, phone/tablet/desktop, keyboard focus, coarse-pointer targets, all-off, rests, duplicates/merged routes, missing geometry, background-style failure and hidden-tab return. Recheck the October tablet issue rather than assume it still exists.
5. Have five people identify the sounding route, focus it, explain focus versus solo, and return to the whole mix. Proposed task criterion: four of five complete without guidance. Record engagement as preference feedback, not a guaranteed retention lift.

State coverage: loading and style failure keep readable routes/status; empty/all-off shows enable guidance; stopped is still; playing uses actual note events; visual focus is separate from hover/audio state; hidden/reduced-motion paths keep the map usable. No per-note screen-reader announcements. Route identity and selected state must remain readable without colour alone.

Recommended first implementation: **quiet basemap + clean legend + visual route focus + zoom-based stop detail**. Refine existing note rings next. Geometry-correct movement follows after those low-risk improvements. No new runtime dependency is needed for this direction.
